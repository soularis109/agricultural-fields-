# Agricultural Fields — моніторинг сільськогосподарських полів

Тестове завдання: SPA для перегляду полів на карті та ведення моніторингових точок (проби ґрунту, шкідники, хвороби рослин тощо). Без бекенду — усі дані mock/in-memory (точки додатково зберігаються в `localStorage`).

## Запуск

```bash
pnpm install
pnpm dev        # http://localhost:5173
pnpm typecheck  # tsc -b --noEmit
pnpm lint       # eslint .
pnpm test       # vitest run
pnpm build      # tsc -b && vite build
```

## Архітектура: доменна структура, не FSD

```
src/
  app/        # вхід, роутер, композиція сторінки (FieldView, AppShell)
  features/
    fields/   # mock-поля, useActiveField, компоненти карти/списку полів
    points/   # типи точок, Zustand-стор, чисті утиліти фільтрації, компоненти
    map/      # MapView + AddPointHandler — композує fields і points
  shared/
    geo/      # єдине місце всіх конвертацій координат (LatLng ↔ GeoJSON ↔ MGRS ↔ Leaflet)
    ui/       # Button — єдиний примітив, реально перевикористаний у ≥2 фічах
    lib/      # formatDate
```

Кожна фіча має `index.ts` як публічний API; імпорти між фічами йдуть лише через нього і через alias `@/` (налаштовано в `tsconfig.app.json`/`vite.config.ts`).

**Напрямок залежностей**: `shared` ← `fields`, `points` ← `map` (композує `fields` + `points`) ← `app`.
`fields` і `points` **ніколи не імпортують одне одного** — `useAddPointFlow` (хук у `map`) бере активне поле через `fields.useActiveField()`, валідує клік через `shared/geo.isPointInField`, а `AddPointHandler` викликає `points.usePointsStore().addPoint(...)` при сабміті форми, передаючи `fieldId`/`fieldName` як прості рядки. Це тримає `points` незалежним від геометрії полів.

Ці правила — не лише домовленість: `no-restricted-imports` у `eslint.config.js` перевіряє їх автоматично (`fields ↔ points` заборонено, `shared` не залежить від фіч/`app`/Leaflet, глибокі `@/features/*/*`-імпорти повз `index.ts` заборонені, гео-бібліотеки — лише в `shared/geo`), тож порушення межі ловить `pnpm lint`.

## Активне поле — тільки в URL

Немає `fieldsStore`: поля статичні (`features/fields/data/fields.ts`), а активне поле береться з `useParams()` через `useActiveField()`. `/` редіректить на перше поле; невідомий `fieldId` рендерить `<FieldNotFound>` — валідний стан, а не помилка роутера.

## Стейт-менеджер: чому Zustand

| Критерій | Context API | Redux Toolkit | **Zustand** |
|---|---|---|---|
| Боілерплейт | ручний reducer/actions | slices, store, typed hooks | один `create()` |
| Ре-рендери | усі споживачі контексту, якщо не дробити вручну | гранулярні через селектори | гранулярні через селектори, без Provider |
| Відповідність обсягу задачі | ризик зайвих ре-рендерів мапи при частих кліках | надлишково важкий для 2 невеликих сутностей | влучний розмір, легко пояснити на ревʼю |

Обрано Zustand: застосунок інтерактивний (часті point-level оновлення від кліків по карті), а домен невеликий — RTK був би виправданим для суттєво більшого застосунку, Context API незручний саме через продуктивність без ручного дроблення контекстів.

**Важливо**: жоден селектор стору не повертає `.filter()`/`.sort()` — у Zustand v5 такий селектор створює новий масив на кожен рендер і ламає контракт стабільного snapshot для `useSyncExternalStore`, що веде до нескінченного циклу ре-рендерів. Похідний список рахує `useVisiblePoints()` через `useMemo` над сирими `points`/`filters` зі стору, викликаючи чисті функції `filterPoints`/`sortPoints` (`features/points/lib/points.ts`) — саме вони покриті тестами.

## Координати та MGRS

Усередині застосунку єдиний тип — `LatLng = { lat, lng }` (`shared/geo/types.ts`). GeoJSON і turf працюють з `[lng, lat]`, `mgrs.forward()` очікує `[lon, lat]`, Leaflet приймає `LatLngLiteral` (яка збігається з нашим `LatLng`). Усі конвертації ізольовані в `shared/geo` — жоден компонент не звертається до координат за індексом напряму.

`toMgrs()` обгортає `mgrs.forward()` у `try/catch`: бібліотека не завжди валідує вхідні дані (наприклад, `NaN` не кидає виняток), але кидає для значень поза діапазоном — тоді UI показує "MGRS: н/д" замість краху.

Еталонне значення в `shared/geo/mgrs.test.ts` пораховане **іншою** бібліотекою (`geodesy` Кріса Веннеса, github.com/chrisveness/geodesy) — незалежною реалізацією, а не тим самим кодом, що тестується.

## Площа поля — з геометрії, а не з `properties.area`

`fieldAreaHectares()` рахує площу через `@turf/area` з фактичної геометрії. **Приклад GeoJSON у ТЗ містить `area: 45.2`, але обчислення за наведеним полігоном дає ≈78.7 га** — приклад із завдання внутрішньо неузгоджений. Застосунок навмисно довіряє геометрії (єдиному надійному джерелу), а не статичному, потенційно застарілому значенню в `properties`.

## Явна обробка помилок і порожніх станів

- Невідомий `fieldId` → `<FieldNotFound>` з посиланням на перше поле.
- Клік поза межами активного поля → банер-попередження (зникає через 3с), точка не додається.
- Помилка MGRS-конвертації → `null` → "MGRS: н/д" в UI, без падіння.
- `errorElement` на рівні роутера — фолбек для неочікуваних рантайм-помилок, окремо від валідного стану "поле не знайдено".
- Список точок: "Точок ще немає" (0 точок узагалі) відрізняється від "Нічого не знайдено" (0 після фільтрів).

## Явні припущення

- Панель точок показує точки **з усіх полів** одночасно, кожен рядок — з назвою свого поля (у ТЗ це не уточнено явно).
- Фільтр за типом, пошук за описом і сортування діють одночасно на список **і** на маркери карти (обидва живляться з одного `useVisiblePoints()`).
- Форма додавання точки — Leaflet `Popup` на місці кліку, без окремого `Modal`-компонента (він не потрібен для одного використання).

## Тести

```bash
pnpm test
```

46 тестів у 11 файлах:

- `shared/geo/geo.test.ts` — `isPointInField`: точка всередині/зовні полігону.
- `shared/geo/mgrs.test.ts` — конвертація з еталоном із незалежного джерела + fallback на некоректний вхід.
- `shared/geo/area.test.ts` — площа поля з геометрії (`fieldAreaHectares`) і форматування (`formatFieldArea`).
- `shared/geo/polygon.test.ts` — конвертація `[lng, lat]` → `{ lat, lng }`, throw на биту позицію.
- `features/points/lib/points.test.ts` — фільтрація за типом/пошуком, сортування, незмінність вхідного масиву, валідація персистованих даних (`isMonitoringPoint`/`restorePoints`).
- `features/points/lib/pointTypes.test.ts` — `isPointType`/`isSortOrder`.
- `features/points/store/pointsStore.test.ts` — `addPoint` (id/дата), `removePoint`, сетери фільтрів не чіпають `points`.
- `features/points/components/PointForm.test.tsx` — тип за замовчуванням, обрізання опису, скасування.
- `features/points/components/PointFilters.test.tsx` — кожен контрол пише у стор, «Скинути» повертає дефолт.
- `features/points/components/PointList.test.tsx` — «Точок ще немає» / «Нічого не знайдено» / рендер видимих точок.
- `features/map/lib/pointDraft.test.ts` — чернетка точки прив'язана до поля, у якому її створили.

`FieldPolygon`, `PointMarker` і `MapView` свідомо не покриті: Leaflet у jsdom не отримує реальних розмірів DOM — це кандидат на E2E (Playwright), а не на unit-тест.

## Що б я додав, маючи більше часу

- **Довести відокремлення від Leaflet до кінця.** `PointMarker` і `FieldPolygon` (доменні компоненти `points`/`fields`) усе ще напряму рендерять `react-leaflet`-примітиви. Переніс би сам мап-рендеринг у `features/map`, залишивши `points`/`fields` геть незалежними від конкретної бібліотеки карт — без циклічної залежності `points ↔ map`, у яку впирається пряме перенесення фабрики іконок.
- **E2E-тести** (Playwright) на ключовий сценарій: клік по карті → форма → точка з'являється в списку і на мапі.
